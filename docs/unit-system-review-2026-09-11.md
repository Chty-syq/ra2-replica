# 单位系统与配置驱动审查（2026-09-11）

目标：尽量还原原版红色警戒 2 的实际表现，使用现代 C++ 和图形技术提高性能。
本次根据当前主程序、单位/建筑/武器实现以及仓库内 `rules.ini`、`art.ini` 进行静态审查。
下面区分已确认的代码行为、尚未实现的能力和建议方案；没有把资源可显示等同于玩法已完成。
本次未修改运行逻辑，也未新增运行测试或进行原版画面对照。

## 结论与已有基础

目前是“共享资源与演示行为 + 按单位 ID 编排”，还没有完整的配置驱动单位系统。
载具并非每种都有独立的 C++ 实现：当前表内的 25 种载具共用 `RhinoUnitState` 和移动函数。
问题在于类型数据、可用能力、生产流程和表现差异没有通过统一的定义层连接起来。

以下已有实现适合保留并逐步接入新定义层：

| 已有基础 | 当前边界 |
| --- | --- |
| SHP/TMP/VXL/HVA/VPL/调色盘解析、2D 和体素渲染 | 能加载和呈现资源，不代表对应单位的规则和能力已经实现 |
| `BuildingAsset` 与 `BuildingInstance` 分离 | 已有共享资源和实例状态，但实例缺少完整规则定义和能力状态 |
| 建筑放置、建造/收起动画、图层角色和缓存 | 常态图层组合与特殊交互仍有多处 ID 分支 |
| 载具选择、路径规划、转向和移动 | 共享一套地面移动参数，缺少不同移动模式与可靠的动态占用 |
| 犀牛炮塔瞄准、地面开火、弹道和爆炸 | 尚未形成通用武器、伤害和目标处理系统 |
| 基地车部署/收起、工厂出车演示 | 由入口中的单独状态维护，不能自然扩展到多个同类实例 |

资源/实例分离见 [building_system.h](/F:/projects/ra2-replica/src/building_system.h:31)，
载具枚举与共享状态见 [rhino_unit.h](/F:/projects/ra2-replica/src/rhino_unit.h:32)。

## 已确认的问题与缺口

### 1. 同一单位因生成入口不同而拥有不同血量；建筑显示需求覆盖了规则血量

初始犀牛由 `RhinoUnitState` 的默认值获得 700 HP，初始化函数不更新血量；
工厂生产的犀牛则读取 `HTNK.Strength=400`。因此，同一种单位目前存在两个不同的初始血量。

建筑会把规则中的 `Strength` 与按地基尺寸推导的“视觉血量”取最大值。
例如仓库配置中 `GAPOWR.Strength=750`、`Foundation=2x2`，最终被改为 1500 HP。
这会影响血量状态及未来的战斗结算，血条尺寸和分段数量应由显示参数决定。

证据：[初始单位创建](/F:/projects/ra2-replica/src/app_main_ui.cpp:846)、
[默认血量](/F:/projects/ra2-replica/src/rhino_unit.h:71)、
[生产单位血量](/F:/projects/ra2-replica/src/app_main_ui.cpp:964)、
[建筑血量覆盖](/F:/projects/ra2-replica/src/app_main_ui.cpp:798)、
[HTNK 规则](/F:/projects/ra2-replica/assets/settings/rules.ini:6475)、
[GAPOWR 规则](/F:/projects/ra2-replica/assets/settings/rules.ini:8892)、
[GAPOWR 外观](/F:/projects/ra2-replica/assets/settings/art.ini:1905)。

修复方向：所有生成入口调用统一实例创建函数，从类型定义初始化生命值；部署转换单独处理血量比例。

### 2. 工厂生产的基地车没有接入部署能力

侧栏生产的 `AMCV`/`SMCV` 被加入普通 `rhinoTanks` 数组。
部署事件只检查另一份单独维护的 `mcvUnit`，点击普通数组里的基地车只会选中它。
`DeploysInto` 已经存在于配置中，但没有参与能力装配。
此外，基地车状态、转换状态和生产状态都是入口中的单个对象，限制了多实例扩展。

证据：[生产路径](/F:/projects/ra2-replica/src/app_main_ui.cpp:958)、
[部署入口](/F:/projects/ra2-replica/src/app_main_ui.cpp:1032)、
[普通载具选择](/F:/projects/ra2-replica/src/app_main_ui.cpp:1075)、
[AMCV 规则](/F:/projects/ra2-replica/assets/settings/rules.ini:6090)。

修复方向：把部署/收起做成实例能力与通用转换状态机，通过 `DeploysInto`/`UndeploysInto` 关联类型。
每个实体保存自己的转换进度、目标类型和待执行命令。

### 3. 配置尚未控制移动和武器，大多数载具只有显示与移动能力

`rules.ini` 在主程序中用于读取阵营颜色和 `Strength`，没有建立单位、武器、弹头、弹丸定义之间的引用关系。
`Speed`、`ROT`、`Primary`、`Secondary`、`Armor`、`MovementZone` 等没有进入对应的运行系统。

所有载具移动均使用 2.4 格/秒、5.2 弧度/秒的共享常量。
仓库里的犀牛 `Speed=6`、灰熊 `Speed=7`、超时空矿车 `Speed=4` 的差异没有生效。
这些原始数值的单位转换还需要明确和标定，不能直接当成格/秒使用。

武器参数来自全局调试面板；命令和更新函数都明确限制为 `VehicleUnitKind::Rhino`。
灰熊的 `Primary=105mm` 没有被解析，其他带武器的载具也不会自动获得武器能力。
弹丸到达目标仅创建爆炸效果，没有调用单位/建筑生命值结算；采矿、装载、飞行和海军行为也没有对应系统。

证据：[规则读取](/F:/projects/ra2-replica/src/app_main_ui.cpp:742)、
[移动常量](/F:/projects/ra2-replica/src/rhino_unit.cpp:21)、
[调试武器参数](/F:/projects/ra2-replica/src/app_main_ui.cpp:167)、
[开火限制](/F:/projects/ra2-replica/src/weapon_system.cpp:371)、
[武器更新](/F:/projects/ra2-replica/src/weapon_system.cpp:417)、
[弹着效果](/F:/projects/ra2-replica/src/weapon_system.cpp:456)。

这部分主要属于尚未完成的玩法。修复方向是共享系统读取类型定义和实例状态，调试覆盖作为显式的实验功能。

### 4. 所有载具走同一战车工厂出厂流程

点击载具图标后统一查找当前阵营的战车工厂，立即生成载具并赋予同一出厂路径。
载具表包含飞机和舰船，它们也进入这条分支。当前没有根据生产类别、海军属性和前置条件选择工厂，
没有费用、真实生产耗时与队列处理。

仓库配置已经有 `GAWEAP.Factory=UnitType`、`GAYARD.Naval=yes`、
`GAAIRC.Factory=AircraftType`、`DEST.Prerequisite=GAYARD` 等信息。
实际生产匹配需要组合类别、属性与前置条件，不能只比较某一个字符串。

证据：[25 种载具表](/F:/projects/ra2-replica/src/app_main_ui.cpp:88)、
[统一生产入口](/F:/projects/ra2-replica/src/app_main_ui.cpp:942)、
[战车工厂配置](/F:/projects/ra2-replica/assets/settings/rules.ini:8418)、
[船厂配置](/F:/projects/ra2-replica/assets/settings/rules.ini:8676)、
[机场配置](/F:/projects/ra2-replica/assets/settings/rules.ini:8754)。

修复方向：UI 发送生产命令；生产系统校验规则、资金和工厂能力；工厂实例保存出厂状态。
队列归属及多工厂加速规则需按目标原版版本核对，不应由当前单例实现决定。

### 5. 建筑图层中包含必要的外观知识，但缺少通用的状态驱动表达

`completeLayerSpecsForBuilding()` 对电厂、兵营、科技中心、矿场、工厂、机场、船厂等逐个判断。
其中一部分只是相同的“主体 + ActiveAnim”；另一部分确有特殊图层、出厂遮挡和动画阶段要求。
这些知识有价值，应转成有状态条件的表现配置。

当前默认分支把 Idle、Active、Special、Super、Production 动画全部加入完成态图层列表。
它无法表达“维修臂仅在维修时伸出”“特定图层只在出厂时启用”等条件；新增资源可能出现不合适的同时播放。
现有代码注释已指出船厂停靠动画和维修臂动画不能全部常驻，但相应处理仍依赖建筑名称。
具体画面差异仍需场景对照确认。

证据：[类型分支](/F:/projects/ra2-replica/src/building_system_runtime.cpp:325)、
[工厂图层](/F:/projects/ra2-replica/src/building_system_runtime.cpp:384)、
[状态相关注释](/F:/projects/ra2-replica/src/building_system_runtime.cpp:419)、
[默认图层组合](/F:/projects/ra2-replica/src/building_system_runtime.cpp:450)。

修复方向：保留共享建筑加载器和图层绘制能力，增加表现配置中的图层角色、启用条件和动画状态。
现有 `art.ini` 解析结果不足以表达这些关系，可以加入项目自己的补充配置。

### 6. 动态占用和模拟时序会影响多单位行为与帧率一致性

地图格子只有 `occupied` 布尔值，没有占用者身份；寻路把 `isBuildable` 当作通行判断。
路径执行时没有重新检查下一格，因此两个单位在规划后可能进入同一格，离开时还可能释放对方的占用。
工厂内部出车也需要受控的通行许可，后续不能简单把所有占用格一律禁止进入。

模拟时间由每个显示帧的实际耗时乘速度倍率直接推进。移动更新每次最多消耗一个路径节点，
到达节点后未利用本次步长的剩余时间；较长帧可能降低实际移动速度。
武器更新同样每次最多发射一次，跨过多个开火周期时不会补算。
因此高显示帧率与低显示帧率的行为一致性还没有得到保证。

证据：[占用数据](/F:/projects/ra2-replica/src/map_grid.h:23)、
[通行判断](/F:/projects/ra2-replica/src/pathfinding.cpp:118)、
[移动执行](/F:/projects/ra2-replica/src/rhino_unit.cpp:295)、
[模拟时钟](/F:/projects/ra2-replica/src/app_main_ui.cpp:676)、
[开火更新](/F:/projects/ra2-replica/src/weapon_system.cpp:451)。

修复方向：按移动类别查询地形，增加占用者和下一格预留；建立固定模拟步长及独立显示插值。
固定步长的频率、长帧追赶策略和原版时间单位换算应明确定义并验收。

## 建议的系统边界

```text
rules.ini + art.ini + 项目补充配置
                  ↓ 加载、校验、解析引用
           DefinitionRegistry
       类型 / 武器 / 弹头 / 弹丸 / 表现定义
                  ↓ 按能力创建
           实体 ID + 类型 ID + 实例状态
                  ↓ 命令与固定模拟更新
     移动 / 战斗 / 生产 / 采矿 / 部署系统
                  ↓ 显示快照和表现事件
        动画 / 音效 / 渲染 / UI
```

- **类型定义**：血量、装甲、速度、转向、武器引用、生产类别、价格、前置条件、能力和资源引用。
  加载时将字符串引用转换为稳定的类型 ID，校验缺失引用与非法数值。尚不支持的关键能力应给出明确诊断。
- **实例状态**：实体 ID、所属玩家、类型 ID、位置、生命值、命令、冷却、路径、生产/采矿/部署进度。
  资源由资源管理器共享，实例持有句柄。避免通过数组下标长期引用可能被删除或移动的实体。
- **能力系统**：C++ 实现通用算法，配置决定组合和参数。例如灰熊与犀牛共享地面移动和炮塔武器；
  矿车组合移动、采矿与卸矿；基地车组合移动与部署；电厂组合静态占地与供电。
- **表现定义**：解析 Rules.Image、Art.Image、Cameo、动画信息及项目资源目录映射。
  地基、炮塔、枪口、图层排序和状态动画由明确字段表达，渲染系统读取模拟结果。
- **共享范围**：建筑、车辆、步兵可以共用生命值、归属、选择、武器和命令接口；
  静态建筑、地面载具、舰船和飞机保留各自的移动、占用和表现模式。
  不必把所有类型的全部状态塞进一个结构，也不必立即引入完整 ECS 框架。

配置能组合已经实现的能力；遇到新的行为机制，仍需要先在 C++ 中实现相应能力。
例如传送、伪装、装载乘员后切换武器，都需要定义各自的行为和状态转换。

## 分阶段迁移与验收

| 顺序 | 工作范围 | 可验证结果 |
| --- | --- | --- |
| 1 | 一次解析 INI，建立类型注册表、统一实例创建与参数转换；优先接入 HTNK/MTNK | 初始与生产的同型单位血量一致；配置改动能影响速度、转向、武器引用；缺失定义报告节名和键名 |
| 2 | 提取固定步长世界更新、占用管理和通用武器/伤害系统 | 犀牛与灰熊使用各自的武器；目标生命值正确变化；不同显示帧率下同一命令序列结果一致；拥堵与工厂通道有回归场景 |
| 3 | 提取生产与部署系统，UI 只发命令 | 多辆生产出来的基地车可独立部署；生产匹配工厂能力；状态互不覆盖；未实现的类型不会被当作完整能力单位生产 |
| 4 | 将现有建筑图层分支迁移为表现配置和动画条件 | 工厂出车、船厂停靠、维修状态正确选择图层；迁移前后的已标定画面保持一致 |
| 5 | 逐项增加采矿、空军、海军和特殊能力 | 每项能力有可重复场景，并与目标版本原版对照 |

第一阶段应连通已有单位的实际执行路径，再逐步扩展覆盖范围。
常规单位的验收标准是：在所需能力已有实现的前提下，通过配置和素材定义新增同类单位，无需新增该单位 ID 的行为分支。

## 与现代 C++ / 图形性能目标的关系

`ArtIni::building()`、`animation()` 当前每次重新打开并扫描文件；
可在加载阶段建立索引，通过显式重载替代查询时的重复 I/O。
运行时使用已解析的类型 ID、共享资源和连续状态容器，避免在每帧重复查字符串或解析配置。

模拟层独立于 SDL/OpenGL，有利于测试、回放和批量场景验证；
渲染继续使用现有素材解码与 GPU 管线，在原版观感约束下逐步做资源共享、实例化和批次合并。
具体收益应通过 CPU/GPU 帧耗时、加载时间和内存测量确认。
数据驱动架构本身不会自动解决透明遮挡、体素光照或获得确定的性能提升。
