# 从零复刻《红色警戒 2》：游戏资源提取与分类整理

> 本文是 RA2 Replica 开发记录的第一篇。我们的最终目标不是做一个只能展示几张图片的 Demo，而是逐步搭建一套能够读取原版配置、渲染建筑与载具、处理阵营色、剧场切换、建造、移动和战斗的运行时。本篇先解决所有后续工作的地基：怎样取得资源，以及怎样让数千个原始文件变成可维护的项目资源库。

## 1. 为什么先做资源治理

《红色警戒 2》的一个对象通常不是一个独立文件。以犀牛坦克为例，车体、炮塔和炮管分别保存为 VXL，组件动画与相对变换又分别保存在 HVA 中；渲染时还需要剧场单位调色盘和 `voxels.vpl`。建筑更加复杂，一个完整建筑可能由主体、底层、常态动画、建造动画、损坏帧和不同剧场变体共同组成。

如果把所有提取结果直接平铺到程序目录，短期内确实能快速显示一张图，但很快会遇到四类问题：

- 不知道某个文件属于哪个对象，也不知道是否漏掉配套文件；
- 同一逻辑对象存在温带、雪地、城市等变体，容易加载错误；
- SHP、UI、特效和 VXL 使用的调色盘不同，文件能打开但颜色不正确；
- 发布包被大量未使用资源占满，而且无法判断哪些文件可以删除。

因此，本项目把资源处理设计成一条单向供应链：

```text
合法持有的游戏安装目录
        ↓  从 MIX 容器提取原始格式
assets_origin（完整、只读的原始资源池）
        ↓  按功能挑选并复制
assets（项目实际使用、按语义组织的运行时资源）
        ↓
资源定位器 → 格式解析器 → CPU/GPU 渲染器
```

## 2. 先认识原版资源格式

游戏安装目录中的大量内容被封装在 MIX 容器中。提取时应保留原始格式，不要先转成 PNG、OBJ 等现代格式，否则会丢失帧索引、调色盘索引、法线索引或组件动画等运行时信息。

| 格式 | 主要内容 | 开发时需要保留的信息 |
| --- | --- | --- |
| `MIX` | 资源归档容器，也可能嵌套其他 MIX | 文件名、来源归档和覆盖优先级 |
| `INI` | 单位、建筑、武器、动画和剧场配置 | 对象 ID、资源名、图层、尺寸、速度等语义 |
| `SHP` | 建筑、步兵、UI、图标和特效的索引色逐帧图像 | 帧尺寸、帧偏移、像素索引、透明色 |
| `PAL` | 256 色调色盘 | 每个索引对应的 RGB，不能脱离使用场景随意混用 |
| `VXL` | 载具或建筑部件的体素数据 | 体素颜色索引、法线索引、包围盒和坐标范围 |
| `HVA` | VXL 各 section 的逐帧变换 | 组件层级、平移、旋转和动画帧 |
| `VPL` | 体素颜色在不同光照级别下的查表数据 | 调色盘、光照级别和颜色映射表 |
| `TMP/TEM/SNO/URB` | 不同剧场的等距地形块 | 地块像素、子格、坡度、高度和剧场语义 |
| `PCX` | 菜单、载入画面等界面图像 | 原始尺寸和调色盘信息 |
| `AUD` | 音效和语音 | 编码参数及采样数据 |
| `FNT` | 原版位图字体 | 字形表、字符映射和间距 |

这里最重要的一点是：SHP 和 VXL 中保存的主要是“颜色索引”，不是最终屏幕颜色。真正的颜色来自 PAL 或 VPL。资源文件和它应使用的调色盘必须一起被视为依赖。

## 3. 从 MIX 中提取资源

### 3.1 准备工作

只从自己合法持有的游戏副本中提取资源。原版资源受版权保护，适合用于本地研究和兼容性实验，不应跟随公开源码仓库重新分发。因此本项目将完整资源池 `assets_origin` 写入 `.gitignore`，代码仓库只记录目录规范和加载逻辑。

准备一个独立工作目录，不要直接修改游戏安装目录。使用能够读取 Westwood MIX 的工具打开归档，XCC Mixer 是常用选择。提取时要注意 MIX 可能嵌套，并且资料片或补丁归档可能覆盖基础归档中的同名文件。

推荐按以下顺序操作：

1. 复制或只读访问原始 MIX，保留一份未修改的游戏安装目录。
2. 展开顶层 MIX 及其中嵌套的归档。
3. 导出 SHP、PAL、VXL、HVA、INI 等原始文件，不执行图像格式转换。
4. 若不同归档出现同名文件，先按来源归档分别保存，不要静默覆盖。
5. 记录资料片、语言版本和补丁版本；它们会影响最终得到的文件。
6. 完成提取后再按资源类型汇总到 `assets_origin`。

理想情况下可以额外维护一份 `manifest`，记录“文件名、来源 MIX、文件大小、校验值”。当前项目已经完成按类型汇总，但来源清单仍是后续值得补强的一环，尤其适合处理同名文件覆盖问题。

### 3.2 原始资源池结构

当前项目把完整提取结果整理为下面这些稳定分类：

```text
assets_origin/
├── audio/       # AUD 音效和语音
├── config/      # rules.ini、art.ini 等配置
├── fonts/       # FNT 字体
├── language/    # 本地化与语言相关资源
├── palettes/    # PAL 与 voxels.vpl
├── sprites/     # SHP 精灵
├── terrain/     # TEM、SNO、URB 等地形块
├── ui-images/   # PCX 等界面图片
└── voxels/      # VXL 与 HVA
```

截至本文对应的项目快照，`assets_origin` 约有 5,900 个文件，其中包括 2,132 个 SHP、184 组 VXL/HVA 组件，以及约 3,100 个剧场地形文件。这个目录的职责是“找得到原始文件”，而不是直接提供给游戏运行时。

可以用 PowerShell 快速检查提取结果：

```powershell
Get-ChildItem .\assets_origin -Recurse -File |
  Group-Object Extension |
  Sort-Object Count -Descending |
  Select-Object Count, Name
```

若某一类数量明显为零，先检查是否漏提取了嵌套 MIX，不要等到渲染阶段再用缺失文件异常排查。

## 4. 建立精简的运行时资源库

`assets` 与 `assets_origin` 的区别不是“新旧版本”，而是“生产输入”和“运行时依赖”：

| 目录 | 是否完整 | 是否允许整理 | 是否进入发布包 | 主要用途 |
| --- | --- | --- | --- | --- |
| `assets_origin` | 尽可能完整 | 不修改原文件 | 否 | 检索、比对、补充资源 |
| `assets` | 只含当前需要的文件 | 按项目语义分类 | 是 | 程序加载和自动化校验 |

当前 `assets` 约保留 530 个文件，目录如下：

```text
assets/
├── settings/                    # 当前使用的 rules.ini、art.ini
├── palettes/
│   ├── theater/                 # unittem、unitsno、uniturb、iso* 等
│   ├── ui/                      # cameo、mouse、palette、sidebar 等
│   ├── effects/                 # anim.pal
│   └── voxel/                   # voxels.vpl
├── buildings/
│   ├── allied/<building-id>/
│   └── soviet/<building-id>/
├── vehicles/<unit-name>/        # 一个单位的全部 VXL/HVA 组件
├── infantry/                    # 步兵资源预留
├── ui/
│   ├── sidebar/<theme>/
│   └── unit_overlays/common/
├── icons/cameo/<category>/
├── effects/
│   ├── projectiles/
│   ├── muzzle/
│   └── explosions/
└── terrain/                     # 地形系统预留
```

分类时遵循四条规则：

1. 第一层表达功能系统，例如建筑、载具、UI、特效，而不是文件扩展名。
2. 多文件对象必须有自己的目录，目录内保留原版文件名。
3. 配套调色盘按使用语义归档，不按“看起来颜色相近”选择。
4. 每次只从 `assets_origin` 复制确实需要的文件，不直接移动或修改原件。

## 5. 如何找齐一个对象的全部资源

### 5.1 从配置文件追踪资源名

资源接入应从 `rules.ini` 和 `art.ini` 开始，而不是凭文件名猜测。

`rules.ini` 描述游戏对象本身，例如对象 ID、`Image`、生命值、武器、速度和建造条件；`art.ini` 描述它怎样呈现，例如建筑主体、建造动画、常态动画、底层、占地和剧场替换规则。常用追踪顺序是：

```text
rules.ini 中的对象 ID
    ↓ Image= 或同名约定
art.ini 中的图像条目
    ↓ 主体、动画、Bib、Buildup、NewTheater
在 assets_origin 中查找对应 SHP/VXL/HVA
    ↓
确定所需 PAL/VPL
```

配置文件名通常不区分大小写，但项目目录统一使用小写，原始文件名本身不做语义改写。这样既便于跨平台，又能继续对照原版配置。

### 5.2 案例：犀牛坦克

犀牛坦克不是单个 `htnk.vxl`，完整模型由三组资源组成：

```text
assets/vehicles/rhino_tank/
├── htnk.vxl          # 车体体素
├── htnk.hva          # 车体 section 变换
├── htnktur.vxl       # 炮塔体素
├── htnktur.hva       # 炮塔变换
├── htnkbarl.vxl      # 炮管体素
└── htnkbarl.hva      # 炮管变换
```

渲染这组文件还需要 `palettes/theater/unit*.pal` 提供剧场单位颜色，以及 `palettes/voxel/voxels.vpl` 提供体素光照查表。建造栏图标则是另一套 UI 资源，应放在 `icons/cameo/vehicles/htnkicon.shp`，并使用 `cameo.pal`。

### 5.3 案例：盟军重工

盟军重工展示了 SHP 建筑为什么必须按对象建目录：

```text
assets/buildings/allied/gaweap/
├── gaweap.shp        # 常态主体
├── gaweap_1.shp      # 出厂状态分层
├── gaweap_2.shp
├── gaweap_3.shp
├── gaweap_4.shp
├── gaweap_a.shp      # 动画层
├── gaweap_b.shp
├── gaweapbb.shp      # bottom/bib 类底层
├── gaweapmk.shp      # 建造动画
├── ggweap*.shp       # 其他剧场变体
├── gtweapmk.shp
└── guweapmk.shp
```

这里任何一个文件被漏掉，都可能表现为建造预览不完整、常态动画错误、出厂遮挡关系错误或切换剧场后没有变化。目录必须以“完整对象”为管理单位，而不能只复制第一眼看到的主体 SHP。

### 5.4 案例：UI 与特效

UI 和特效也必须按使用场景绑定调色盘：

| 资源场景 | 当前项目使用的调色盘 |
| --- | --- |
| 建造 cameo | `palettes/ui/cameo.pal` |
| 鼠标指针 | `palettes/ui/mousepal.pal` |
| 血条与单位覆盖层 | `palettes/ui/palette.pal` |
| 爆炸、炮口火焰 | `palettes/effects/anim.pal` |
| 盟军/苏军侧栏 | `palettes/ui/sidebar/sidec01.pal`、`sidec02.pal` |
| VXL 载具 | 当前剧场的 `unit*.pal` + `voxels.vpl` |

“颜色不对”通常不是 SHP 解码失败，而是选错了 PAL。判断调色盘时应先看资源语义，再看文件名和原版配置，不能靠肉眼试到一个大致相似的结果。

## 6. 让代码适应分类目录

资源分类后，加载器不能再假设所有文件都位于同一层。本项目从当前目录向上寻找包含 `assets` 的项目根，然后集中建立 `settingsRoot`、`buildingRoot`、`paletteRoot`、`vehicleRoot` 等路径。对应实现位于 `src/demo_app_support.cpp`。

建筑和 cameo 在各自搜索根下建立递归文件索引，按小写文件名查找。这使 `buildings/allied/gaweap/gaweap.shp` 仍可通过原版 ID `GAWEAP` 定位，同时避免每帧递归扫描磁盘。

这种方案有一个必须遵守的约束：同一搜索根内的文件名应全局唯一。当前索引以文件名为键，如果两个目录包含同名文件，只有其中一个会进入索引，而且遍历顺序不应被当成可靠的覆盖规则。发现重复名称时，应明确拆分搜索根或给加载器增加优先级，而不是依赖目录顺序。

## 7. 每次引入新资源的标准流程

以后接入一个新单位、建筑或特效时，按下面的清单执行：

1. 在 `rules.ini` 中确认对象 ID、`Image`、武器和相关动画条目。
2. 在 `art.ini` 中确认主体、附加动画、建造动画、底层和剧场规则。
3. 在 `assets_origin` 搜索全部相关文件，并检查同名前缀的组件。
4. 将文件复制到 `assets` 对应对象目录，保留原始文件名。
5. 同时确认 PAL、VPL、cameo、弹体、炮口和爆炸等跨系统依赖。
6. 检查同一搜索根是否出现重复文件名。
7. 启动时做缺失资源校验；错误信息应包含对象 ID 和缺失文件名。
8. 分别验证温带、雪地、城市剧场以及不同阵营色。
9. 确认运行时不再访问 `assets_origin`，发布包只依赖 `assets`。

## 8. 本阶段的验收标准

资源整理完成不等于“目录看起来整齐”，而应满足以下可验证条件：

- 删除或临时移开 `assets_origin` 后，程序仍能启动并运行已有功能；
- 所有运行时路径都从统一的 `DemoAppPaths` 或专用资源定位器获得；
- 一个多组件单位的文件能在一个目录内完整审阅；
- SHP、VXL、UI 和特效都有明确的调色盘归属；
- 剧场切换不会因为缺少变体而静默回退到错误素材；
- 缺失资源能在加载阶段以明确错误暴露，而不是渲染成空白；
- `assets_origin` 不进入 Git，也不进入最终发布包。
