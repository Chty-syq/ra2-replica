# 当前实现缺口与后续顺序

日期：2026-09-16。依据当前源码、配置、测试和已有实现记录检查。
本次只做评估，未修改程序源码。重跑现有 Debug 构建的 12 项 CTest，全部通过。
这不等于原版兼容性验收，也不是新一轮性能测量。

当前阶段：配置驱动的 RTS 模拟与渲染原型，能够演示局部战斗和建造，尚未形成完整对局。
不建议给整体还原度一个百分比：不同兵种、场景和规则的覆盖差异很大，尚无完整原版对照基线。

## 已经具备的基础

- C++20，共享核心/模拟/表现/渲染模块，无图形核心可独立测试。
- 统一读取规则、类型定义和资源映射，多个地面车辆和建筑实例共用系统。
- 固定游戏帧、速度档位、位置/朝向插值、命令排序和确定性状态摘要。
- 地面 A*、占用和预留、显式攻击、基础伤害与死亡、车辆生产队列及厂内出车。
- 基地车展开/收起、建筑施工和工作图层、血条与选中显示。
- SHP/TMP/VXL/HVA 等基础资源读取，调色盘/VPL 渲染和按类型资源缓存。
- 有本项目回归场景、无图形模拟基准和首轮规则时序校准。

409 个配置类型被导入，不代表 409 个类型的完整玩法已实现。
当前武器执行条件主要限定为单发、带 Arcing 的普通主武器；步兵、海空和许多特殊机制被拒绝或尚未表达。

| 声音 | 主程序只初始化视频，没有完整游戏声音链路 | 命令语音、武器/爆炸/建筑音效、EVA 提示和音乐 |

具体证据：

- `src/simulation/world.h` 的 CommandKind 当前仅含 Move、Stop、AttackGround、AttackEntity、Deploy、Produce、CancelProduction、PlaceBuilding。
- `src/config/definitions.cpp` 已读取 Power，但 World 没有电力汇总或用电系统。
- `World::apply(PlaceBuilding)` 直接创建正在施工的建筑；没有建筑生产完成后待放置的中间状态。
- `src/sidebar.cpp` 有维修/出售按钮状态，但主程序未将这些状态接为对应的世界命令；雷达目前是界面贴图。
- `src/app_main_ui.cpp` 只有一个 selected 实体 ID，场景是固定初始布置，主循环没有对局 AI、胜负或音频推进。
- `MapGrid::inBounds` 始终返回 true，宽高是沙盒元信息。

## 配置架构还欠的部分

通用系统已建立，不能再概括成“每种坦克都写一套逻辑”。但目前主要能力仍集中在 `World::Impl`，
定义也是有限字段组成的结构，离完整的可组合能力系统还有以下距离：

1. **能力支持报告。** 当前 unsupported 只识别部分字段；未读取的规则可能没有诊断，
   因此“能创建该类型”并不能保证其特殊规则得到支持。需要列出已实现、近似实现、不支持和忽略字段，并保留来源。
2. **可复用活动。** 采矿、卸矿、停靠、攻击移动等需要可组合的持续活动，避免继续增加互相影响的状态标志。
3. **系统边界。** 新增经济、供电、视野时，应把它们分别组织成系统；World 保留调度、实体生命周期和命令入口。
4. **表现事件。** 现有快照适配可用，但还需要稳定的动画/声音事件和状态条件，驱动受伤、死亡、断电、装卸等表现。
5. **旧适配清理。** Rhino 命名的通用绘制结构、旧模拟辅助函数、巨炮显示特例和部分图标映射仍存在；迁移时维持现有截图回归。
6. **持久化与联机。** 当前只有进程内命令回放测试和状态摘要，没有正式存档/读档、录像文件、网络命令同步或断线恢复。

这些不要求推翻当前 EnTT 和配置导入方案，应在新增具体能力时逐步拆分。

## 性能工作的真实进度

已具备按类型缓存、固定模拟帧、带预算的寻路、VPL/调色盘 GPU 渲染。
`drawRhinoPartSections` 已通过 `glDrawArraysInstanced` 绘制单个部件的体素，
因此不能说“完全没用实例化”。但这不等于把多辆同型车辆合并为一次或少量绘制。

尚缺大型真实场景的 CPU/GPU 分项测量。现有基准只覆盖无渲染的静止与稀疏短路径移动，
不覆盖交战、密集拥堵、成片建筑、动画、选中血条和资源切换。

值得测量的候选点，而非已经证实的瓶颈：

- 主循环多次完整生成 `world.snapshot()`，包括仅为显示实体数量而创建快照。
- 每次命中遍历全部实体；需要时可利用空间查询缩小范围。
- 每辆车的遮挡重绘先扫描全部建筑，规模约随车辆数乘建筑数增长。
- VXL 按单位、部件提交，重复设置状态和法线表；缺少跨单位批次。
- 2D 绘制每次上传顶点并提交；血条的多个像素段也分别绘制，适合在维持遮挡顺序的前提下合批。

下一步应先加入真实压力场景、CPU/GPU 时间、绘制次数及 P95/P99，
再决定空间索引、快照缓存、SHP 批处理或车辆批次的优化顺序。此处没有给出未经测量的性能提升承诺。

## 建议推进顺序与验收

| 阶段 | 工作范围 | 验收场景 |
| --- | --- | --- |
| 1：最小经济循环 | 有边界的平坦测试地图、矿区、矿车采集和矿场卸矿、资金到账 | 关闭 Sandbox 后，资金耗尽的玩家能通过采矿恢复生产，多个矿车不会互相卡死 |
| 2：基地运行 | 建筑生产/待放置、电力、科技、维修/出售、工厂集结点 | 从基地车开始建发电厂、矿场、兵营/工厂；缺电和资金不足有正确结果 |
| 3：可打的一局 | 框选/编队、警戒/攻击移动、基础步兵、视野、简单 AI 和胜负 | 玩家可从零发展并与电脑完成一局地面战，包含获胜和失败 |
| 4：表现校准与性能 | 原版固定场景、动作/事件对照、音效、压力场景和热点优化 | 同样规则下可解释时序差异，优化前后行为/截图不回归，并报告实际测量结果 |
| 5：内容扩展 | 海空、运输、特殊单位、超武、复杂地形，随后存档/录像/联机 | 每增加一种机制，都用通用能力服务多个类型，并有独立验收场景 |

回归测试、配置诊断和原版基线应从第一阶段起持续补充；第四阶段是集中验收，不是延后发现基础差异。
如果下一轮只选一项，优先实现“矿车—矿区—矿场—资金”的通用能力链，连同最小地图资源数据。
